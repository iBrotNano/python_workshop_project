# Requirements: ChatBot for nutritional information and recipes

- Issue: [#53](https://github.com/iBrotNano/python_workshop_project/issues/53)
- Milestone: 0.2.0
- Status: Draft - requirements clarified, ready for implementation
- Labels: enhancement
- Branch: `feature` branch created (see issue checklist)

## 1. Summary

Add a command-line chatbot to the application that answers natural-language
questions about products and their nutritional values, proposes alternative
products for a given nutritional goal, and discusses recipes and their
ingredients - including proposing ingredient substitutions to optimize a recipe.
The chat is grounded in the application's own SQLite data (products, ingredients,
recipes). Confirmed recipe optimizations are written back to the database.

## 2. Goals

1. Let a user ask questions about nutrients/products in natural language and get
   answers grounded in the application's data.
2. Let a user state a nutritional goal (e.g. lower sugar, fewer calories) and get
   alternative products/ingredients that exist in the application's dataset.
3. Let a user discuss a recipe, see its ingredients, and ask for optimizations
   (substitutions) - with an explicit confirmation step before anything is saved.
4. Fail gracefully and cheaply when the configured local LLM is missing,
   incompatible, or cannot be loaded.

### Problem being solved

Today nutrition and recipe data can only be inspected through fixed/explicit
commands. Exploring it ("which of these has less sugar?", "what can I swap the
sugar with?") requires manual comparison. Users want to ask directly and get
reasoned answers plus concrete, dataset-backed alternatives.

### Success

The two acceptance tests of the issue are demonstrable end-to-end in a fresh demo
environment (see section 11). No measurable latency or cost target is defined in
this change; they are TBD (see section 13).

## 3. Users and current process

- Single local user operating the application from a terminal (no accounts,
  no multi-user, no web UI).
- Current process: user runs CLI commands, reads tabular/text output, and must
  compare values manually. No LLM is involved today.
- After the change: user starts a chat session and converses; the application
  retrieves matching data via semantic search, the LLM decides which tool to call
  and explains results.

## 4. Scope

### In scope

- Interactive chat mode in the CLI (REPL loop; context kept for the session;
  exit via a documented command/`Ctrl+C`).
- Grounded retrieval over the existing SQLite products/ingredients/recipes data.
- Hybrid semantic/keyword search over that data, built by **`sqlite-rag`** from
  local GGUF embedding models. No cloud embedding calls.
- Three capabilities exposed to the LLM as tools (tool/function calling):
  1. look up product/ingredient nutrition,
  2. find alternatives for a product/ingredient under a user-stated constraint,
  3. propose a recipe optimization (ingredient substitutions).
- Alternatives are restricted to items that exist in the application's dataset.
- Confirmation flow: proposed recipe change is shown as a diff and only persisted
  to SQLite after explicit confirmation.
- One LLM integration: a local GGUF model executed directly through
  **llama_cpp_python**. No OpenAI- or Ollama-compatible service is used.
- Configuration is provided through the application configuration and names the
  local GGUF model plus generation settings.
- Clear, non-traceback error handling when the LLM is missing/unreachable/times
  out, or when the `sqlite-rag` index/embedding model is unavailable.
- Cost/safety guardrails: context/conversation cap, max-token setting, single
  non-medical-advice disclaimer.

### Out of scope (non-goals)

- Web or HTTP UI.
- Multi-user support, authentication, authorization, sessions shared across users.
- Medical or dietary advice; the chatbot does not replace professional advice.
- Automatic/unconfirmed recipe modifications.
- Cloud-hosted embeddings.
- Persistent chat history across runs (in-memory only).

## 5. Functional requirements

### 5.1 Chat session

- FR-1: A CLI entry point starts an interactive chat loop. The user types a
  question per line; the assistant answers in the terminal.
- FR-2: Conversation context is kept in memory for the duration of the session
  only. Nothing is persisted to disk.
- FR-3: The assistant answers in the language of the user's question. UI labels
  and prompts are English.
- FR-4: The session ends on an explicit exit command and on `Ctrl+C`/EOF without
  a traceback.
- FR-5: A one-line non-medical-advice disclaimer is shown at session start.

### 5.2 Grounded nutrition Q&A (acceptance test 1, part 1)

- FR-6: On a natural-language question about a product/ingredient, the app
  performs semantic search over the local index and passes the best-matching
  records (name, per-100 g nutrition fields available in the DB, category) to
  the LLM as tool results.
- FR-7: The LLM must answer only from the retrieved records. If no record matches
  with sufficient similarity, the assistant states that the item is not in the
  database instead of inventing values.
- FR-8: For each answer that cites data, the CLI prints a structured block with
  the matched entries (name, kcal, protein, fat, carbohydrate, sugar, salt -
  whichever fields exist) beneath the prose, so figures are verifiable.

### 5.3 Alternatives under a constraint (acceptance test 1, part 2)

- FR-9: The user states a goal in natural language (e.g. "lower sugar",
  "fewer calories", "more protein"). The LLM maps this to a structured
  constraint and calls the alternatives tool.
- FR-10: The alternatives tool searches the dataset for items comparable to the
  referenced product/ingredient (same category / similar use where the data
  allows) that satisfy the constraint, and returns a ranked, bounded list
  (default top N, configurable).
- FR-11: Only items present in the dataset are proposed. If none satisfy the
  constraint, the assistant says so; it must not invent products.
- FR-12: Each proposed alternative is presented with the concrete values that
  justify it (e.g. sugar per 100 g before vs. after).

### 5.4 Recipe discussion and optimization (acceptance test 2)

- FR-13: The user can reference a recipe by name (or ask what a recipe contains);
  the app retrieves the recipe and its ingredients from the database.
- FR-14: The user can ask to optimize a recipe (e.g. "make it lower in sugar").
  The LLM calls the recipe-optimization tool, which proposes substitutions using
  dataset items only, with a short rationale and the impact on the relevant
  nutrition values.
- FR-15: Proposals are shown as a before/after diff of the ingredient list,
  including amounts if stored, plus the estimated nutrition change where
  computable from stored values.
- FR-16: Nothing is written unless the user explicitly confirms (`y`/`yes`).
  Confirmation applies to one proposal; edits to the proposal require a new
  proposal.
- FR-17: On confirmation, the updated recipe and its ingredient links are written
  to SQLite in a single transaction; on failure the transaction is rolled back
  and the user sees an error. On rejection the database is untouched.
- FR-18: If the recipe no longer exists or changed since it was loaded, the save
  is refused with a clear message (no silent overwrite).

### 5.5 Routing

- FR-19: All user input is handled by the LLM; capability selection happens via
  tool/function calling. No slash-command syntax is required from the user.
- FR-20: Tools are read-only except the explicit save step, which is executed by
  the application only after confirmation (the LLM cannot write to the DB).

## 6. Data and retrieval

- Storage: existing SQLite database holding products, ingredients and recipes;
  the chatbot must reuse the existing data-access layer rather than introducing a
  parallel one.
- Embedding: `sqlite-rag` creates embeddings locally with the configured GGUF
  embedding model (default: `embeddinggemma-300m`, Q8_0). The model is provisioned
  locally before indexing; no network calls are required at query time.
- Nutrition index: `sqlite-rag` persists nutrition vectors, documents, metadata,
  and its FTS5 index in the existing `data.db`. The database maintenance flow
  rebuilds the nutrition index together with a nutrition-data refresh and can
  quantize its vectors after creation.
- Recipe index: recipe embeddings are stored in a separate `data_recipes.db`
  sidecar so recipe changes do not modify the nutrition index. New recipes are
  indexed after their SQLite transaction commits, deleted recipes are cleaned up,
  and a database maintenance action indexes already stored recipes that are
  missing from the sidecar.
- Matching: `sqlite-rag` combines vector similarity and SQLite FTS5 keyword
  retrieval, then ranks the merged results. Retrieval returns top-K candidates;
  K is configurable. If the best score is below a configured threshold, treat
  the item as "not in database".
- Values: nutrition figures are per 100 g/100 ml as stored; the assistant must
  state the basis when presenting values and must not convert unless data exists.

## 7. LLM integration and configuration

- FR-21: The LLM is loaded locally with `llama_cpp_python` from the configured
  GGUF model file. The configuration contains the model metadata/path, chat
  format, and generation settings.
- FR-22: No cloud provider, service endpoint, or API key is required.
- FR-23: The configured GGUF model must support the chat format and tool calling
  used by the application.
- FR-24: Tool/function definitions are passed directly to
  `llama_cpp_python.Llama.create_chat_completion` and support the three tools
  plus the text interface.
- FR-25: Configuration and model-loading errors are caught at session start and
  reported with a hint, without a traceback.

## 8. Error handling and resilience

- FR-26: A missing/incompatible model or model-loading/inference error produces
  a clear single-line error plus a configuration hint; the session exits
  gracefully without a stack trace. Optionally the user may retry the same
  question.
- FR-27: Configured embedding GGUF model unavailable or `sqlite-rag` index
  unavailable/unbuildable -> chat refuses to start in "grounded" mode with an
  explicit message (no LLM-only fallback, since answers must be
  dataset-grounded).
- FR-28: Malformed/unknown tool arguments from the LLM are handled by returning an
  error message to the LLM and continuing the turn; at most a bounded number of
  tool iterations per user turn.
- FR-29: Any exception at the top level is converted into a friendly message;
  a verbose/debug flag may show details.

## 9. Cost, safety, privacy

- FR-30: Configurable max output tokens and a maximum conversation length
  (context window cap with oldest-turn trimming). Defaults documented.
- FR-31: Only data needed for the current question (top-K records) is passed to
  the local LLM; the complete database and conversation are never uploaded.
- FR-32: Recipe/ingredient text is treated as untrusted content: it is passed as
  data, never as instructions, to mitigate prompt injection.
- FR-33: The disclaimer states answers are informational and not medical advice.
- FR-34: No transcript or personal data is written to disk by the chat.
- FR-35: LLM inference runs locally and incurs no per-token provider cost. Output
  and context caps still bound local resource consumption.

## 10. Non-functional requirements

- Performance: interactive response expected; no numeric latency target defined
  (TBD). Index build time is a one-off; query time is bounded by top-K search.
- Scalability: single local user; dataset sizes as currently in SQLite. No
  concurrency requirements.
- Availability: retrieval and inference work offline after the required models
  and index have been provisioned locally.
- Security: no API key, remote LLM endpoint, or remote telemetry is used.
- Privacy/compliance: prompts and retrieved public product/recipe data remain on
  the local machine; no additional regulatory requirements are identified.
- Accessibility: terminal output only, plain text; no special requirements.
- Technical constraints: reuse the existing Python CLI framework and SQLite
  data-access layer; use `llama_cpp_python` for generation and `sqlite-rag` for
  local embedding, indexing, FTS5 search, and hybrid retrieval; do not add
  OpenAI, Ollama, or HTTP-based LLM integrations.

## 11. Acceptance criteria

Derived from the issue's acceptance tests, made verifiable:

1. **Nutrition Q&A** - Given a product/ingredient known to exist in the database,
   when the user asks about its nutrition, then the answer cites the stored values
   and the CLI prints the structured record block. Given an item not in the
   database, then the assistant says it is not found and states no values.
2. **Alternatives** - Given a product and a constraint ("lower sugar"), when the
   user asks for alternatives, then the assistant lists dataset items satisfying
   the constraint with before/after values. If none exist, it says so.
3. **Recipe optimization** - Given an existing recipe, when the user asks to
   optimize it, then a substitution proposal with rationale and a before/after
   diff is shown; nothing is saved until the user confirms; after confirmation the
   recipe is updated in SQLite and visible on reload; on rejection it is
   unchanged.
4. **Graceful failure** - With a missing or unloadable local model, the chat exits
   with a clear message and no traceback; no provider cost is incurred.

Demo: fresh demo environment, run all four scenarios, plus verify the two
original acceptance test checkboxes.

## 12. Dependencies and risks

- Depends on the existing SQLite schema and data-access layer (reuse, no schema
  changes assumed; any needed schema change must be raised separately).
- Depends on `sqlite-rag` and its native SQLite-AI/SQLite-Vector functionality,
  plus a locally provisioned GGUF embedding model; this affects install size and
  offline bootstrap.
- Nutrition embeddings must be rebuilt during the nutrition update flow, while
  recipe embeddings are created incrementally and periodically reconciled with
  the recipe database. Missing or stale embeddings can reduce grounding quality.
- Tool-calling behavior depends on the selected local model and its chat format;
  the model choice must support tools.
- Non-deterministic LLM output makes strict assertions hard; integration tests
  use a real local `llama_cpp_python` model and are inherently fuzzy.
- Local inference performance depends on the host's CPU/GPU resources and the
  selected model.
